# Roadmap

## 기획 세션에서 확정된 것 (2026-08-21)

이 표가 로드맵의 전제다. 여기서 벗어나는 변경은 근거를 대고 이 표를 먼저 고친다.

| 항목 | 결정 |
|---|---|
| 무엇을 만드나 | 범용 API 클라이언트 풀스택 (HTTP + GraphQL + 환경 + 러너), 추후 gRPC |
| 차별점 | GraphQL 깊이, 텍스트 파일 중심 + GUI 보조, 예외 케이스 중심 설계, VS Code 네이티브 품질 |
| 상태 저장 | 파일 + SecretStorage 하이브리드 |
| 파일 포맷 | `.http` 읽기(import) + 자체 포맷 쓰기 |
| 변수 세트 | 환경 × 케이스 2차원 |
| 터널링 | 범위 제외 (API 부재) |
| 배포 | 처음부터 마켓플레이스 공개 |
| GraphQL 최종 범위 | **비주얼 쿼리 빌더 포함** |
| v0.1 절단선 | GraphQL 먼저, HTTP는 백엔드 엔진만 |
| UI | CustomTextEditorProvider + React webview |
| 러너 | 케이스 일괄 실행 + 선언적 어서션 (JS 스크립팅 없음) |
| 라이선스 | MIT |
| 투입 | 주 20시간 이상 |

**주의: 비주얼 쿼리 빌더는 최종 범위에 포함된다.** 다만 v0.1 절단선 결정에
따라 v0.3으로 배치했다(2026-10-06 재정렬 전에는 v0.2). 빠진 것이 아니라 순서가 뒤로 간 것이다.

전제: 주 20시간 투입. 1개월 ≈ 80시간.
아래 시간은 **작업 시간**이고, 달력 기준 기간은 그 옆에 병기한다.

## v0.1: GraphQL 실행기 (170~200h, 8~10주)

목표를 한 문장으로: **인트로스펙션이 꺼진 서버에 대해, 로컬 SDL 파일로
자동완성이 되는 GraphQL 쿼리를, 케이스 4개를 붙여 한 번에 돌린다.**

HTTP는 백엔드 엔진만 만들고 GUI를 붙이지 않는다. GraphQL 전송에 필요한
만큼만이다.

### 최소 동작 정의 (이게 되면 v0.1이다)

1. `.salvo` 파일을 Salvo Editor로 열면(Open With, 에디터 제목 버튼, 커맨드) 요청 편집 UI가 뜬다
2. `salvo.yaml`의 `schema` 키가 가리키는 로컬 SDL 파일(또는 introspection JSON, opt-in URL)을 읽어 스키마를 로드한다
3. 쿼리 에디터에서 필드 자동완성, hover, 검증이 동작한다
4. 케이스 4개(정상/만료/권한없음/토큰없음)를 정의하고 한 번에 실행한다
5. 각 케이스의 `expect`가 통과/실패로 응답 뷰어에 표시된다 (뷰어는 v0.1 포함)
6. 토큰은 SecretStorage에 있고 파일에는 `{{secret:NAME}}`만 남는다
7. `salvo.yaml`에 환경 2개를 정의하고 상태바에서 전환할 수 있다
8. **회사 환경 없이도 동작이 증명된다**: 레포의 `examples/quickstart`가
   공개 데모 GraphQL API를 상대로 그대로 실행된다 (Global-first, 결정 10)
9. 마켓플레이스에 `jungsehui.salvo`로 공개되어 있다 (pre-release 채널)

## v0.2: HTTP 전면 (80~120h, 4~6주)

2026-10-06 결정(사용자): 범용 API 테스트 도구 포지셔닝에 맞춰 GraphQL 깊이보다
먼저 한다. 마켓 설명과 실제 기능의 간극을 가장 빨리 줄인다. 하위 프로젝트로 나눠
하나씩 스펙, 플랜, 구현을 거친다. 첫 하위 프로젝트는 HTTP 코어(메서드 전체,
json/text/form 바디, Basic 인증, 비주얼 에디터는 GraphQL과 같은 수준)이고
0.2.0으로 낸다. 스펙: `docs/superpowers/specs/2026-10-07-http-core-design.md`.

- 메서드 전체, 헤더 편집, body 6종 (json / form-urlencoded / multipart / raw / binary / graphql)
- auth (bearer / basic / apikey / oauth2 / aws sigv4)
- `.http` 파일 import (REST Client / httpYac 문법 → `.salvo` 변환)
- 응답 뷰어 강화

## v0.3: GraphQL 깊이 (120~160h, 6~8주)

Bruno에 없는 세 개를 여기서 확보한다. **차별점의 절반이 이 마일스톤에 걸려 있다.**
기획 단계에서 "빌더까지 전부"로 합의했고, v0.1 절단선 결정에 따라 여기로 왔다.

- 스키마 문서 브라우징 전용 패널
- 오퍼레이션 히스토리 (`workspaceState`)

빌더 단독으로 40~60h를 잡는다. 이 프로젝트 최고 난이도 모듈이다.

# 만들지 않을 것

| 항목 | 이유 |
|---|---|
| **터널링** | stable API에 Tunnel이 없다(직접 확인, 0건). `asExternalUri`는 로컬에서 no-op이고, proposed API는 `vsce`가 publish를 거부한다. VS Code 내장 Ports 뷰를 README에서 안내한다 |
| **성능 트레이스 / 필드 사용량 통계** | 서버에 `ApolloServerPluginInlineTrace`를 붙이거나 GraphOS에 리포팅해야 성립한다. 회사 게이트웨이는 `ApolloServerPluginUsageReportingDisabled()`로 리포팅을 의도적으로 차단 중이다. 운영 텔레메트리 영역이지 에디터 도구 영역이 아니다 |
| **스키마 레지스트리 / 그래프 관리** | GraphOS의 유료 코어다. git이 이미 그 역할을 한다 |
| **클라우드 동기화 컬렉션** | 파일 + git이 대체한다. 계정을 만드는 순간 Postman과 같은 자리로 간다 |
| **JS 스크립팅 (pre/post-request)** | 샌드박스, 타임아웃, 보안 설계 비용이 선언적 어서션 대비 과하다 |
| **CLI / CI 러너** | v1.0 이후. 별도 패키지와 배포 파이프라인이 생긴다 |
| **계정 / 로그인** | Postman과 Thunder Client가 여기서 신뢰를 잃었다 |
| **텔레메트리** | "기본 off"가 아니라 아예 없다. Bruno가 확장에서 텔레메트리를 no-op으로 만든 선례를 따른다 |
| **Windows / Linux 1급 지원 (v0.1 한정)** | macOS에서 먼저 검증한다. 크로스 플랫폼 이슈는 HTTP 전면(v0.2) 이후 |

# 위험 요소

우선순위 순이다.

**1. Bruno가 쿼리 빌더를 확장에 이식한다 (가능성은 추측)**
데스크톱 앱에는 v3.3.0부터 있다. 확장 쪽 부재는 파일명 grep 기반 관찰이라
확정이 아니다(research.md 미확인 참조). 이식되면 v0.3 차별점의 절반이 사라진다.
완화: 케이스 모델(방어 가능한 유일 차별점)을 v0.1에 확실히 심는다.
빌더는 "있으면 좋은 것"이지 존재 이유가 아니라는 위치를 유지한다.

**2. ~~LSP 서버와 자체 포맷의 접합~~ 해소됨 (2026-08-21 스파이크)**
LSP 서버를 쓸 필요가 없었다. `graphql-language-service`의 순수 함수를
직접 호출하면 되고, 246KB 사내 스키마로 7개 함수 전부 실측 통과했다.
접합부라는 것이 애초에 존재하지 않는다. 상세는 `architecture.md` 결정 6.

남은 잔여 리스크는 작다. fragment 해석, 파일 감시, 문서 관리를 우리가
직접 해야 하지만, 셋 다 자체 포맷이므로 어차피 우리 몫이었다.

**3. UI 컴포넌트 전량 자체 제작**
`@vscode/webview-ui-toolkit`이 2025-01 deprecate되고 레포가 아카이브됐다
(GitHub API `archived: true` 확인). 공식 대체재가 없다. Microsoft 입장은
"확장 작성자가 직접 책임진다"이다.
완화: v0.1 UI를 의도적으로 빈약하게 간다. 예쁨은 그 뒤 마일스톤에서.

**4. ~~대형 SDL 파싱 성능~~ 해소됨 (2026-08-21 실측)**
246KB federation 2 SDL의 `buildSchema`가 cold 20.3ms / median 13.9ms,
382KB가 cold 26.0ms다. 콜드 경로 총합 약 72ms로 100ms 안에 들어온다.
워커도 캐시 계층도 필요 없다.

대신 다른 것이 드러났다. `require('graphql')`가 49.6ms로 파싱보다 비싸다.
**`activate()`에서 graphql을 require하지 않는다. lazy load한다.**

그리고 사내 SDL 5개 중 2개가 파싱 또는 빌드에 실패한다(`research.md` 참조).
스키마 로드 실패는 예외가 아니라 1급 시나리오로 다뤄야 한다.

**5. 자체 포맷 채택 저항**
사용자가 기존 컬렉션을 다시 쓰기 싫어한다. `.http` import(v0.2 HTTP 전면)까지는
마이그레이션 경로가 없다.
완화: v0.1은 애초에 신규 GraphQL 작업만 노린다. 대량 이전을 요구하지 않는다.

**6. 마켓플레이스 공개 후 유지보수 부담**
REST Client가 open PR 61건으로 사실상 죽었고, 평점 4.91에도 릴리스가
4년 멈췄다. 혼자 하는 프로젝트의 표준 실패 모드다.
완화: 이슈 템플릿과 응답 SLA를 처음부터 낮게 공표한다. 과대 약속하지 않는다.

**7. 마켓플레이스 첫인상 (리뷰 추가)**
"범용 API 클라이언트"로 이름 걸고 GraphQL 전용 v0.1을 내면 REST 사용자가
설치하고 1~2점을 남긴다. 평점은 회복되지 않는다(레퍼런스: graphql-execution
평점 2.00). 2026-10-04 결정(사용자): 마켓 표시는 범용 API 테스트 도구로 간다. 완화책은 둘이다.
설명에 현재 지원 범위를 그대로 적고, `rest` 키워드는 REST 실행이 들어가는 0.2.0에서
넣는다. 2026-10-06 정정: 0.1.0이 이미 정식 채널에 올라가 있어서 0.1.x는 정식 채널로
낸다(pre-release 완화책은 적용되지 않았다). 평점은 되돌릴 수 없으므로
설명이 아직 없는 기능을 약속하지 않게 한다.

**8. ~~GraphOS Studio Explorer 접근~~ 해소됨 (2026-08-21 실사용 확인)**
Explorer는 완전히 동작하고 프론트 팀이 활발히 쓴다. 그러나 Developer 플랜
좌석 10/10 만석이고 백엔드는 개인 좌석 없이 공용 관리자 계정으로만 접근한다.
판매 문구는 예정대로 재조정했다: 케이스 모델 + 좌석·계정 없음 +
미publish 로컬 스키마 + 에디터 통합. 상세는 `research.md`의
"GraphOS Studio 실측" 섹션.
